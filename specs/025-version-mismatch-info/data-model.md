# Phase 1 — Data Model: More Informative Version Mismatch Indication

**Feature**: 025-version-mismatch-info
**Date**: 2026-04-09

## Scope

This feature is **frontend-only and derives from existing data**. No changes to `data/current.json`, no new backend fields, no new database tables. This document inventories the existing fields the frontend reads and defines one new **derived** in-memory structure (the `MismatchClassification`) that lives only inside the browser.

---

## Existing fields consumed (read-only)

### `CurrentData.cityGroups[].environments[]`

Source: generated by `src/index.ts:157-163` from `resolveEnvironment()`.

| Field | Type | Description |
|-------|------|-------------|
| `id` | `string` | e.g. `"tampere-prod"`, `"tampere-staging"` |
| `type` | `"production" \| "staging"` | Used by the overview to label the row `Tuotanto` or `Testaus`, and by this feature to pick between `"tuotannossa"` / `"testauksessa"` in the warning text |
| `version` | `VersionSnapshot` | Representative snapshot displayed in the row badge |
| `versionMismatch` | `boolean` | True iff more than one unique SHA is present among OK-status instances |
| `mismatchDetails` | `VersionSnapshot[]` | When `versionMismatch` is true, contains **every** fetched instance snapshot (both OK and non-OK — see note below). Empty array otherwise. |

**Note on `mismatchDetails` content**: `src/index.ts:162` currently passes `resolved.versions` (all fetched versions, including non-OK). The classifier in this feature filters to `status === 'ok'` before tallying (FR-006). We rely on existing behaviour and do not change the set passed in.

### `VersionSnapshot` (unchanged)

| Field | Type | Description |
|-------|------|-------------|

## New derived type (frontend only, in-memory)

### `MismatchClassification`

**Lifetime**: created by `classifyMismatch(mismatchDetails)` and immediately consumed by the rendering functions. Never persisted, never serialised.

**Location**: defined in `site/js/lib/mismatch-classifier.js` as a plain JSDoc typedef (the codebase is vanilla JS ES modules — no TypeScript files under `site/`).

```js
/**
 * @typedef {Object} AbnormalInstance
 * @property {string} instanceDomain       - e.g. "varhaiskasvatus.tampere.fi"
 * @property {string} label                - Short display label: instanceDomain.split('.')[0]
 * @property {string|null} sha             - The full SHA this instance is pinned to (core preferred, wrapper fallback), or null if neither
 * @property {string|null} shortSha        - 7-char short SHA for display
 */

/**
 * @typedef {Object} MismatchClassification
 * @property {boolean} hasMismatch         - True if >= 2 distinct SHAs exist among OK instances
 * @property {boolean} isTied              - True if no single largest group exists
 * @property {string|null} majoritySha     - The SHA shared by the largest group, or null when isTied or !hasMismatch
 * @property {number} majorityCount        - How many OK instances share the majority SHA (0 when isTied)
 * @property {AbnormalInstance[]} abnormalInstances - Instances whose SHA differs from the majority (empty when !hasMismatch; every OK instance when isTied)
 * @property {number} okInstanceCount      - Total OK-status instances considered in the tally
 */
```

### Classification rules (enforced by `classifyMismatch`)

1. Filter `mismatchDetails` to `snapshot.status === 'ok'`.
2. If fewer than 2 snapshots remain → return `{ hasMismatch: false, isTied: false, majoritySha: null, majorityCount: 0, abnormalInstances: [], okInstanceCount: 0|1 }`.
3. Group by `snapshot.coreCommit?.sha ?? snapshot.wrapperCommit?.sha ?? ''`.
4. If fewer than 2 distinct group keys → same "no mismatch" return shape as step 2.
5. Sort groups by descending count.
6. If the top group's count is strictly greater than the second group's count:
   - `majoritySha = topGroup.sha`, `majorityCount = topGroup.count`, `isTied = false`.
   - `abnormalInstances` = every OK snapshot NOT in the top group, mapped to `AbnormalInstance`.
7. Else (tie):
   - `majoritySha = null`, `majorityCount = 0`, `isTied = true`.
   - `abnormalInstances` = **every** OK snapshot, mapped to `AbnormalInstance`.
8. Always `hasMismatch = true` in cases 6 and 7.

### Invariants the renderer can rely on

- `hasMismatch === false` ⇒ `abnormalInstances.length === 0` and `majoritySha === null`.
- `hasMismatch === true` ⇒ `abnormalInstances.length >= 1`.
- `isTied === true` ⇒ `abnormalInstances.length === okInstanceCount`.
- Non-OK snapshots (`unavailable`, `auth-error`) are never present in `abnormalInstances`. The renderer keeps their existing status class untouched (FR-006).

## Entity relationship (conceptual)

```
CityGroup (1) ── (n) Environment (1) ── (n) VersionSnapshot  (existing, unchanged)
                               │
                               └── versionMismatch: bool
                                   mismatchDetails: VersionSnapshot[]
                                        │
                                        └── classifyMismatch() ─► MismatchClassification  (new, derived)
                                                                         │
                                                                         └── abnormalInstances[]
```

## Validation / consistency notes

- The classifier performs no I/O and throws no errors. Malformed input (e.g., a snapshot with neither `coreCommit` nor `wrapperCommit`) is grouped under the empty-string key and treated as a regular group. In practice the backend always produces at least one commit per OK snapshot.
- If `mismatchDetails` is `undefined` or `null` (current backend emits `[]`, but defensive programming), the classifier treats it as an empty array.
- Output is deterministic: `abnormalInstances` is ordered by the original `mismatchDetails` array order, so the rendered warning text list is stable across reloads.
